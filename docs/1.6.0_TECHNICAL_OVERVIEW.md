# Generator Accelerator 1.6.0
## 1. Главная идея версии

Раньше GA в основном ускорял отдельные горячие места worldgen: noise, surface,
features, biome lookup, carvers, структуры и контейнеры блоков. В `1.6.0` мод
двигается в сторону полноценного runtime-backend для генерации чанков.

Проще говоря:

- Minecraft решает, какие чанки и статусы можно запускать.
- GA решает, как именно выполнить тяжелую работу быстрее и безопаснее.
- Результат должен возвращаться в обычные vanilla chunk objects в стабильном
  порядке.

Поэтому в версии появились scheduler, chunk pipeline, workspace, commit engine,
transaction sandbox, mailbox и расширенная диагностика.

## 2. GA Scheduler

`GAScheduler` - это общий планировщик работы GA. Он разделяет задачи по lanes:

- `noise` - тяжелые вычисления шума и генерации;
- `compile` - прогрев и компиляция планов;
- `workspace` - работа с chunk workspace;
- `transactional` - изолированные worldgen units;
- `serial` - задачи, которые нельзя безопасно распараллелить;
- `commit` - финальное применение результатов обратно в chunk state.

Зачем это нужно:

- не запускать все подряд в одном общем пуле;
- не создавать неконтролируемый nested parallelism;
- держать отдельную очередь для опасных или строго упорядоченных операций;
- иметь throttling по CPU, heap usage, commit backlog и mailbox backlog.

Количество worker'ов и лимиты очередей можно менять через config/system
properties.

## 3. Chunk-status pipeline и custom chunk graph

Minecraft генерирует чанк по статусам: biomes, noise, surface, carvers,
features, spawn и так далее. В `1.6.0` GA добавляет слой, который может
перехватывать выполнение этих статусов и отправлять их в свои scheduler lanes.

Важные части:

- `GAChunkStatusPipeline` - переносит тело отдельных chunk statuses в GA runtime.
- `GACustomChunkGraphScheduler` - строит более прямой граф готовых chunk tasks и
  старается не ждать лишние layer barriers.
- CAS guards - защищают области чанков, куда status может писать.
- per-status config flags - можно включать/выключать ускорение отдельно для
  biomes, noise, structures, surface, carvers, features и spawn.

Это не просто "еще один thread pool". Смысл в том, чтобы запускать работу тогда,
когда зависимости готовы, и не ломать порядок видимых side effects.

## 4. GA Chunk Workspace

`GAChunkWorkspace` - это chunk-local рабочая копия данных. Она нужна, чтобы
горячий worldgen не писал каждый блок сразу в тяжелые vanilla structures.

Идея:

1. Импортировать нужные данные чанка в быстрый локальный формат.
2. Выполнить terrain/surface/decoration работу над этим локальным состоянием.
3. Собрать dirty sections и применить изменения обратно одним контролируемым
   этапом.

Это помогает уменьшить:

- количество мелких random writes в vanilla chunk sections;
- overhead от `PalettedContainer`;
- лишние проверки и аллокации на каждый блок;
- contention между потоками.

При этом самые агрессивные режимы workspace-only writes и parallel decoration
journals оставлены экспериментальными и выключены по умолчанию. Инфраструктура
есть, но runtime выбирает безопасный путь, если не уверен в корректности.

## 5. Commit engine и mailbox

Когда несколько задач могут писать в чанк или соседние чанки, важен порядок.
Если просто дать потокам писать напрямую, можно получить race condition или
разный результат от запуска к запуску.

Для этого появились:

- `GACommitBatch` - пачка изменений;
- `GACommitOrderKey` - стабильный ключ порядка;
- `GACommitOwnership` - понимание, кто владеет изменением;
- `GACommitConflictGroups` - группировка конфликтующих записей;
- `GACommitEngine` - финальное применение;
- `GACrossChunkMailboxRuntime` - очередь для записей в соседние чанки.

Простая модель: тяжелые задачи считают результат параллельно, но запись обратно
проходит через контролируемый и детерминированный слой.

## 6. Transaction sandbox

Не весь modded worldgen безопасен для параллельного запуска. Некоторые моды
читают/пишут глобальное состояние, создают side effects или ожидают vanilla
порядок вызовов.

Transaction sandbox - это слой для таких случаев:

- задача может работать в изоляции;
- ее записи попадают в journal;
- journal можно проверить;
- затем результат либо применить, либо отправить в fallback/serial path.

Это основа для будущего безопасного ускорения неизвестного worldgen-кода без
грубого `synchronized` вокруг всего Minecraft.

## 7. Decoration Pipeline

Decoration Pipeline ускоряет `ChunkGenerator.applyBiomeDecoration`.

Вместо того чтобы каждый раз проходить сложные vanilla списки features и
placement modifiers, GA строит более компактное представление:

- `DecorationPlacementProgram` - быстрый план placement modifiers;
- `SectionDescriptor` - описание секции для предварительного отсева;
- biome/feature caches - кеши для повторяющихся списков;
- metrics - счетчики, чтобы видеть fallback, compile и execution cost;
- read snapshots и journals - задел для безопасного параллельного decoration.

Если feature слишком сложный или небезопасный, pipeline должен уйти в fallback,
а не пытаться "ускорить любой ценой".

## 8. Surface Rule Compiler

Surface generation - это много повторяющихся проверок правил, биомов, высоты,
шума и блоков. В `1.6.0` surface path стал более data-oriented:

- surface rules компилируются в компактную программу;
- секции обрабатываются через masks и raw block ids;
- `VectorBlockColumn` и `VectorChunkContext` уменьшают количество объектов;
- неизвестные rules или несовместимые cases уходят в vanilla fallback;
- добавлены метрики для surface compiler.

Важная совместимость: если ModernFix владеет своим surface optimization path,
GA отключает свой `buildSurface` rewrite и связанные MixinSquared compat hooks
для Biolith/BWG/NatureSpirit, чтобы не падать на отсутствующем handler'е.

## 9. Biomes, structures, carvers и fluids

Кроме больших систем, версия содержит много точечных ускорений:

- быстрый biome/climate lookup через плоские индексы и raw sampling;
- Biolith и TerraBlender compat для biome search;
- более безопасный structure data access;
- кеш carver plans на чанк;
- быстрые writer'ы для carving;
- оптимизации fluids и block-light/source checks;
- ускорения для отдельных vanilla и modded features.

Такие изменения меньше видны архитектурно, но они убирают много CPU и GC шума в
горячих местах генерации.

## 10. Density compiler и native cleanup

Density Function Compiler остается Java/JIT-ориентированным ускорителем.
В `1.6.0` вокруг него стало больше lifecycle, metrics и fallback-защиты.

## 11. Совместимость с C2ME, ModernFix, Lithium и worldgen модами

В `1.6.0` GA стал аккуратнее отключать чужие mixin'ы, когда они конфликтуют с
тем же hot path.

## 12. Diagnostics

Диагностика теперь важная часть архитектуры.

Обычному игроку она не должна мешать: по умолчанию heavy diagnostics выключены.
Оператор может включить сбор данных командой `/ga diagnostics start` или
сбросить/снять bundle через `/ga diagnostics`.

Диагностика собирает:

- JSON snapshot;
- JFR events;
- scheduler/workspace/commit metrics;
- decoration pipeline metrics;
- surface compiler metrics;
- DFC and Feature VM metrics;
- worldgen profiling counters.

Это нужно, чтобы разбирать реальные модпаки не наугад, а по данным.

## 13. Что включено не полностью

Некоторые системы уже есть в коде, но самые рискованные режимы не являются
безусловным fast path:

- workspace-only block writes выключены по умолчанию;
- known decoration journal writes выключены по умолчанию;
- decoration conflict scheduler выключен по умолчанию;
- неизвестный modded worldgen не считается автоматически потокобезопасным;
- fallback и serial/transaction paths остаются обязательной частью дизайна.
